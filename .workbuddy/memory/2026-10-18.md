## FSToast 最后一个 UIKit 实现清掉

`FSToast.toast(_:duration:to:)` 原来是 `UILabel` + `UIView` 手搓：量文字宽高（`FSCalculator`）、
造 label、造深灰圆角块、`addSubview` 到宿主、两段 `UIView.animate` 淡入淡出、延时移除。
现改为一行转发 `FSToastCenter.shared.show(text, duration:)`，**与不带 `to:` 的调用同一条路径**。

- `to:` 参数保留（类型 `UIView` → `AnyObject?`），内容**忽略**：93 处调用点一行不用改。
  `_ =` 写法仍编译通过（只多一条 "`_` on Void is redundant" 警告，与现存的
  `_ = FSToast.toast("换组成功")` 同类，不是新问题）。
- 文件不再 import UIKit 相关类型，`FSCalculator` / `WIDTHFC` 依赖一并消失。
- 行为变化 1 处：toast 从「宿主 view 居中」变成「屏幕居中」（`AppRootScreen` 的
  `FSToastOverlay` 是全局浮层）。`to:` 传值不再影响任何东西。

校验：用桩 `FSToastCenter` 建了 `/tmp/toastcheck/FSKit.swiftmodule`，
`swiftc -typecheck` 跑通 FSToast.swift + 五种旧调用写法（含 `to:` 传非可选/可选/`_ =`）。
**纯源码校验，未跑 xcodebuild 构建。**

## FSToast 宽度改为内容自适应

`FSKit/FSKit/Classes/FSToastCenter.swift` 的 `FSToastOverlay`。

病根：`frame(maxWidth: WIDTHFC - 50)` 挂在 `Text` 上（`background` 内侧）。`Text` 收到被夹到
上限的提议后，`frame` 自身就撑满 343pt，`background` 自然也是一整条 —— 短文案同样显示成固定宽的大长块。

改法：把宽度上限**挪到 `background` / `clipShape` 之外**，顺序变成
`Text → font → padding(.horizontal,10) → frame(minHeight:40) → fixedSize(horizontal:false, vertical:true)
 → background → clipShape → frame(maxWidth: maxWidth) → allowsHitTesting(false)`。
`Text` 在有限提议下是 tight-fit，短文案按内容宽，超长才吃满上限并居中换行。
抽出 `private var maxWidth: CGFloat { WIDTHFC - 50 }`（值不变）。未加最小宽度。

验证：`swiftc -typecheck`（桩 `WIDTHFC`，exit 0）+ 在 macOS 用 `ImageRenderer` 把改前/改后
5 组文案渲染成 PNG 对比（`/tmp/toastlayout/`），确认短文案贴内容宽、长文案换行且不超宽。
**未跑 xcodebuild。**

## alertInput 弹出效果 vs 系统 alert：实测（未改代码）

用户反馈「alertInput 的弹出效果不如系统 alert」。在 `/tmp/alertlab` 建了一个探针 App
（`swiftc` 直接编 .app bundle + simctl install，无需 xcodeproj），在 **iPhone 17 Pro / iOS 26.5**
上对系统 `UIAlertController` 做了逐帧采样 + 像素分析 + layer 动画 dump。

### 系统 alert 的精确规格（iOS 26 Liquid Glass）

| 项 | 实测值 |
|---|---|
| 面板 | 320 × 264，圆角 **34**（`_UIAlertBackground.layer.cornerRadius`） |
| 面板垂直位置 | y=319（874 高屏）= **safeArea 内居中**（59 + (781-264)/2 ≈ 317.5），不是整屏居中 |
| 遮罩 | `view.alpha` 0→1，底层黑色约 0.2（背景 200 → 160） |
| 入场曲线 | `CASpringAnimation` damping=**45.71** stiffness=**522.35** mass=**1** v0=**0** duration=**0.404**（ζ 恰好 = 1.0，无回弹） |
| 面板 transform | **恒 1.0，没有缩放** |
| 按钮布局 | **横排 2 个**，各 140×48，间距 8，左右边距 16，圆角 ≈ 24（capsule） |
| 输入行高 | **48**（不是 45），输入块圆角 ≈ 16 |
| 面板亮度 | rgb(201)，**边缘有 ~19pt 宽的高光/折射带 rgb(228)**（仅 Liquid Glass 有） |

层级（关键，改代码时别找错层）：
```
UITransitionView
 ├ UIView              ← 遮罩，alpha 0→1 动画挂在这
 └ _UIAlertControllerPhoneTVMacView (320×264)
     └ _UIAlertInterfaceActionGroupView
         └ _UIAlertBackground  ← cornerRadius 34 / masksToBounds
```

### 材质对照实验（同一灰背景 + 0.2 遮罩，单点采样）

`regularMaterial` 232 / `thinMaterial` 213 / `ultraThinMaterial` 190 /
`glassEffect(.clear)` 185 / `Color.white.opacity(0.43)` **201**（数值命中系统）/ 系统 201。

**没有一档能同时匹配亮度和模糊**：white 0.43 数值对但完全不模糊；ultraThin 模糊像但偏暗且
没有边缘高光；`.glassEffect` 在 overFullScreen 场景下过度透明、还出现 content 重影 artifact。
⇒ **纯 SwiftUI 自绘不可能完全复刻 iOS 26 的玻璃。**

### 当前 FSUIKit 的差距

竖排按钮（系统是横排）/ 圆角 28（34）/ 行高 45（48）/ 面板 232（201）/
入场是 `easeOut(0.3)` 淡入 + `spring(0.42, 0.86)` 从 0.94 放大（系统是纯 opacity 的 ζ=1 spring）。

⇒ 已把两条路的取舍报给用户（换回 `UIAlertController` 本尊 vs 自绘精修），**等用户定，未改代码**。

### 探针手法可复用

- 无 xcodeproj 建 iOS 测试 App：`swiftc -target arm64-apple-ios18.0-simulator -swift-version 5
  -parse-as-library -Xfrontend -disable-sandbox`，然后塞 Info.plist + `codesign -s -`。
- 读像素：`sips -s format bmp` → 自己解析 BMP（compression=3 要处理 BITFIELDS mask）。
- 拿系统动画参数：present 后同步遍历 layer 的 `animationKeys()` → `debugDescription`。
  异步读会太晚（动画已移除），但同步读时视图可能还没进 window，需微调时机。
- `-UIAnimationDragCoefficient 10` 在本机模拟器上**没生效**；simctl 录像是 VFR，抽帧抓不到中间帧。
